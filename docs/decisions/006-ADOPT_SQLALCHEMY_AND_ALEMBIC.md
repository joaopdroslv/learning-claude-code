# ADOPT_SQLALCHEMY_AND_ALEMBIC

**ID:** ADR-006
**Timestamp:** 2026-05-25 15:25
**Status:** Accepted
**Type:** feature

## Context
With dev MySQL already running (ADR-003) and a Python toolchain pinned (ADR-004), the project needs an ORM layer and a migration tool so schema changes are version-controlled rather than ad-hoc DDL. SQLAlchemy + Alembic is the canonical pairing in the Python ecosystem and is what the `mysql-dev` subagent's prompt was already hinting at ("schema is defined by SQLAlchemy models...").

## Decision
- **SQLAlchemy 2.0** with the new `DeclarativeBase` + `Mapped[...]` typing style.
- **Alembic** for migrations, configured to read its database URL from the project's `.env` via `app.db.DATABASE_URL` instead of `alembic.ini`. This keeps one source of truth — `alembic.ini`'s `sqlalchemy.url` is left blank.
- **PyMySQL** as the driver (pure Python — no C compiler required on Windows). `cryptography` is pinned so PyMySQL can speak MySQL 8's default `caching_sha2_password` auth.
- **Connection URL is host-aware**: `app/db.py` reads `MYSQL_HOST` from the environment. The dev container's compose file sets `MYSQL_HOST=mysql` (the compose service name) so the URL inside the container resolves over the docker network; from the Windows host the same `.env` keeps `MYSQL_HOST=127.0.0.1` and traffic goes through the published port. `python-dotenv.load_dotenv()` runs with the default `override=False`, so the in-container override wins.
- **Layout**:
  - `app/db.py` — engine, `SessionLocal`, `Base`.
  - `app/models/__init__.py` — re-exports every model so `Alembic` autogenerate sees them.
  - `app/models/customer.py` — first model.
  - `migrations/`, `alembic.ini` — generated by `alembic init migrations` at the repo root (renamed from the tool's default `alembic/` to follow the broader Python web convention of `migrations/`), with `env.py` patched to import `app.db.Base` + the models and override `sqlalchemy.url`.
- **Customer schema** (as requested): `id` PK autoincrement, `full_name` (varchar 255), `email` (varchar 255, unique + indexed), `age` (int), `birthdate` (date), `created_at`/`updated_at` (datetime, `server_default=NOW()`). `updated_at` uses SQLAlchemy's app-side `onupdate=func.now()` — the migration does *not* emit `ON UPDATE CURRENT_TIMESTAMP`. See Consequences below.

## Alternatives considered
- **Tortoise ORM / Django ORM / Peewee**: heavier or framework-coupled. SQLAlchemy is the Python community default and gives the widest hiring/onboarding signal.
- **`mysqlclient` instead of PyMySQL**: faster (C extension) but requires a C compiler and MySQL headers at install time, which trips Windows contributors. PyMySQL is good enough for dev; can swap later if perf becomes an issue.
- **Raw migration SQL committed under `migrations/`**: simpler, but loses autogenerate and the rollback story. Alembic's overhead is small and the diff-against-models flow is exactly what we want.
- **Keep `sqlalchemy.url` in `alembic.ini`**: standard pattern but means credentials in two places (or `.ini` and `.env`). Putting it in `env.py` (sourced from `app.db.DATABASE_URL`) keeps `.env` the only credential file.
- **Store `age` as a derived/computed column** (or drop it and compute from `birthdate`): correct data-modelling instinct, but the spec explicitly listed `age`. Kept as a plain int; future ADR can normalize if it causes drift.

## Consequences
**Positive:**
- `alembic revision --autogenerate -m "..."` diffs the live MySQL schema against `Base.metadata` and writes a migration file under `migrations/versions/`. The Customer migration was generated this way and creates the `customers` table + a unique index on `email`.
- Same code path on host (`MYSQL_HOST=127.0.0.1`) and in dev container (`MYSQL_HOST=mysql`), with no per-environment branching in `app/db.py`.
- Models added under `app/models/` are picked up by autogenerate automatically as long as they're imported from `app/models/__init__.py`.

**Negative:**
- `updated_at` only auto-updates when SQLAlchemy issues the UPDATE — raw SQL updates won't bump it. To get true server-side behavior we'd need to either (a) drop the Python-side `onupdate` and add `ON UPDATE CURRENT_TIMESTAMP` to the column DDL via a raw `alembic.op.execute(...)` step, or (b) attach a trigger. Deferred until something actually writes outside SQLAlchemy.
- `age` is denormalized — storing it alongside `birthdate` means we'll have to keep them in sync (or accept that `age` may be stale).
- PyMySQL is slower than `mysqlclient` at high QPS. Not relevant at our current scale.
- `cryptography` is a heavy transitive dep (pulls `cffi`), but it's needed for MySQL 8 auth and is already a common transitive of many tools.
