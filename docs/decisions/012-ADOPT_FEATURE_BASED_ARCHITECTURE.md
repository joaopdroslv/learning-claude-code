# ADOPT_FEATURE_BASED_ARCHITECTURE

**ID:** ADR-012
**Timestamp:** 2026-07-08 14:52
**Status:** Accepted
**Type:** feature

## Context

The project is growing into a fake-bank domain: an asynchronous API that enqueues operations
to Kafka, workers that process them, an append-only **ledger** as the source of truth, and a
**balance projection** rebuildable by replaying that ledger. The central legal entity every
account and ledger entry hangs off is the **client**, and a client is either an **individual**
(pessoa física / PF, identified by CPF) or a **company** (pessoa jurídica / PJ, identified by
CNPJ) — different attributes that a single flat table cannot represent honestly.

Two concrete constraints forced a decision now, on the first real feature:

1. **Domain.** The only model was `customers(full_name, email, age, birthdate)` (introduced in
   ADR-006). It had no client type, no PF/PJ split, and `age` duplicated `birthdate`. There was
   nowhere for accounts/ledger to attach a typed owner.
2. **Structure.** The codebase was layer-based (`app/models/`), with no FastAPI app, no Pydantic
   typing, and no feature boundaries — a shape that does not scale to the planned features
   (accounts, ledger, workers) without scattering each domain across layer folders.

Because this is the first feature, it also had to establish the conventions the rest of the
project follows. This ADR does not supersede ADR-006 (SQLAlchemy + Alembic still stand); it
replaces the specific `customers` model that ADR-006 introduced.

## Decision

- **Feature-based (vertical-slice) layout.** Each feature is a package under
  `app/features/<feature>/` owning its own models (one SQLAlchemy model per file), Pydantic
  schemas, and — as it grows — router/service/repository/worker. Shared infrastructure stays in
  `app/db.py` (engine, session, `Base`) and a new `app/core/`. Alembic discovers models through
  `app/core/metadata.py` (one import line per feature); `migrations/env.py` imports only that
  module, so migrations never pull in FastAPI.
- **FastAPI + Pydantic v2** as the HTTP and typing layer: validate at the edges, split
  `...Create` (input) from `...Read` (output), and use discriminated unions for polymorphic
  shapes. (No routers/app in this first slice — data layer only.)
- **Clients via SQLAlchemy joined-table inheritance.** A base `clients` table holds the common
  columns plus a `type` discriminator; `individuals` (PF) and `companies` (PJ) each key off
  `client_id` (PK **and** FK to `clients.id`). The `type` enum is stored **by value**
  (`individual`/`company`, via `values_callable`) so the DB representation matches Pydantic/JSON.
- **Migration reset.** The old `customers` model and its base migration were deleted and a fresh
  `create_clients` migration autogenerated against an empty database.
- **Formalized** in `docs/standards/architecture.md`, `@`-imported by `CLAUDE.md`.

## Alternatives considered

- **Layer-based layout** (`app/models/`, `app/routers/`, `app/services/`): rejected — as
  features multiply, each domain's code scatters across layer folders; a feature stops being a
  thing you can reason about in one place.
- **Single-table inheritance for clients** (one `clients` table, nullable PF/PJ columns + a
  `CHECK`): simpler and JOIN-free, but subtype columns cannot be `NOT NULL` at the DB level and
  the table widens with every new attribute. Rejected in favor of per-subtype constraints.
- **Separate independent PF/PJ tables** (no shared parent): rejected — accounts and the ledger
  would need a polymorphic FK to reference "a client of either type", which is messy and loses a
  single `client_id`.
- **Storing the enum by member name** (SQLAlchemy's default, uppercase `INDIVIDUAL`/`COMPANY`):
  rejected — the DB value would diverge from the lowercase Pydantic/JSON value. Used
  `values_callable` to store the member value instead.

## Consequences

**Positive:**
- Accounts and the ledger reference a single `client_id`, regardless of client type.
- Each subtype enforces its own columns `NOT NULL` and its own unique key (CPF/CNPJ) in its own
  table.
- Adding a feature means adding a self-contained package, not editing shared layer folders.
- Pydantic validates input at the edge (CPF/CNPJ shape, email); DB and API speak the same enum
  values.

**Negative:**
- Joined inheritance needs a JOIN to read a full client, and an insert touches two tables.
- The convention adds ceremony: per-feature packages and one `app/core/metadata.py` import line
  to maintain per feature.
- New dependency (`pydantic[email]`) and a new standards doc to keep current.
- CPF/CNPJ validation is shape-only for now (11/14 digits); check-digit validation is deferred.
